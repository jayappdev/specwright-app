# SpecWright

SpecWright is a desktop app that turns a written spec into working code. Its default "Spec workflow" is built on GitHub Spec Kit (`/speckit.constitution` → `/speckit.specify` → `/speckit.clarify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`) through the Claude Code CLI or the GitHub Copilot CLI, with a human approval gate after every step.

## Stack

| Layer | What |
|---|---|
| Shell | Go 1.26, Wails v2.17.1 (the only direct dependency). System webview. `app.go` exposes `core.Hub` to the UI. |
| Headless | `cmd/headless` runs workflows with no window, lists history and replays runs. |
| Spec Kit | SpecWright does not ship GitHub Spec Kit. It downloads the latest release on this computer, through the proxy, CA and package index under **Packages & proxy**: either when those are first saved, or at the first **Choose input › Set up Spec Kit**. It runs Spec Kit's own CLI (`specify init`, via uv, pipx or a Python venv) from `github.com/github/spec-kit` and caches the output per version in the app's data folder. Setup creates the project in its own folder (`specify init <project>`). It writes the selected skills, rules and tools into a managed block of `CLAUDE.md` / `.github/copilot-instructions.md`, and each workflow step runs its own `/speckit-<step>` skill inside that folder. A workspace can hold several projects (**Project › + New project…**). Each has its own workflow progress, inputs and history (`.codegen/workflows/speckit@<folder>.json`), while the wizard's skills, rules, tools and proxy are shared. **Download project (.zip)** exports the selected project. Headless: `-init claude\|copilot -project <folder>`. |
| Frontend | React 19 (no other runtime libraries), bundled by esbuild 0.25 into `frontend/dist`, which `main.go` embeds. |
| Themes | Three families plus three skins. GitHub: seven Primer VS Code themes in `frontend/src/themes.generated.js` (generated by `scripts/build-themes.mjs`). Copilot (six) and Android/Material 3 (six seeds × dark/light, or any seed color as `m3:#rrggbb:dark`) are computed in `frontend/src/palettes.js` from seed colors with OKLCH tonal palettes. Five styles (skins): Workbench, Console, Paper, Material (Roboto, pill buttons, navigation rail) and Copilot (Mona Sans, gradient buttons). Interface and code fonts can be overridden; Roboto, Roboto Mono, Mona Sans, Inter and JetBrains Mono (SIL OFL, Fontsource dev dependencies) are bundled into `dist/fonts` via `frontend/src/fonts.css` (Latin subsets only, ~380 KB). |
| Browser preview | `frontend/src/mockBackend.js` stands in for the Hub so the UI runs in a plain browser. |

### Internal packages

- `agent`: Claude (`claude -p --output-format stream-json`), Copilot (`copilot -p … --allow-all-tools`) and a scripted mock. All output is normalized into events.
- `session`: per-run state machine (idle → running → paused → done / failed / cancelled / interrupted).
- `workflow`: steps, approval gates, retries, token/cost/premium-request budgets, prompt composition, the step runner.
- `store`: redacted JSONL run history, the usage ledger (`usage.jsonl`) and replay. Kept in the user config dir (`~/Library/Application Support/codegen` on macOS).
- `watch`: stdlib polling watcher; file changes are attributed to the running step with +/− line counts.
- `loop`: detects repeated tool calls or replies; the run pauses at a "loop" gate.
- `bus`: in-process event bus. Every event is redacted before fan-out.
- `extension`: tools in `<workspace>/.codegen/extensions.json`, a token-protected loopback HTTP bridge, and the `agentbridge` MCP server (`SpecWright agentbridge`) exposing one tool, `extension_managed`.
- `core`: the `Hub` that wires everything.

### Tools (extensions)

- **Language priority:** "Runs in: Auto" writes new tools in the first language installed on the machine, in the order Node.js → Go → Java → Bash. Java is only counted when a JDK actually runs, not the macOS `/usr/bin/java` stub. You can also pick a language yourself.
- **Fix with AI:** when "Test with AI" fails, this button sends the failed checks, command and output to the agent. It applies the revised tool and tests again, up to 3 attempts. It can't fix a missing secret; set the value under Secrets first.
- **Output shape and JSON parameters:** a tool that prints JSON can declare the shape of its output (paste example JSON or a JSON Schema, or **Learn it from the last test**), and a parameter of type `json`, `object` or `array` can declare its shape. The Flow designer uses them to show fields and check paths. Declaring them does not change the tool's approval. The agent is only given a JSON parameter's shape (compactly, when it fills it in); the output shape is never sent to the AI.

### Tool dependencies, local package repositories and the corporate proxy

- **Dependencies:** a tool can list packages under Review › Dependencies, e.g. `pg@8.13.1` (Node.js), `psycopg[binary]==3.2.3` (Python), `github.com/jackc/pgx/v5@v5.7.1` (Go) or `org.postgresql:postgresql:42.7.4` (Maven). The AI adds them itself when it needs a driver or SDK.
- **Tool folder:** such a tool gets its own folder, `.codegen/tools/<scope>/<name>/`, containing its entry file and manifest (`package.json`, `requirements.txt` plus `.venv`, `go.mod` plus `bin/`, or `pom.xml` plus `lib/`). The app writes its run command.
- **Installs:** dependencies install when you test or save a tool, and again on first use after a fresh clone. They come through the workspace-local package repositories in `.codegen/cache/{npm,pip,go-mod,m2}`, which are git-ignored.
- **Packages & proxy (wizard section 7):** overrides the HTTP/HTTPS proxy, no-proxy list, corporate CA bundle, npm registry, pip index, GOPROXY/GOPRIVATE/GONOSUMDB/GOSUMDB/GOTOOLCHAIN and the Maven mirror. Empty fields inherit what the machine already uses, shown in grey.
- **Where it's saved:** `.codegen/packages.json`. Proxy passwords stay in memory only and are masked in the UI.
- **Maven:** it reads no proxy variables, so the app writes `.codegen/cache/maven-settings.xml` (private file) with the mirror, proxy and local repository.
- **Check connections:** fetches a small file from each registry through the configured proxy.
- **Agents and builds:** an optional switch also applies the proxy and registries to Spec Kit agent runs and "Compile project" (Maven through `MAVEN_ARGS`).
- **What each language needs:** `npm` for Node.js, `python3` for Python, `go` for Go, and `mvn` plus a JDK for Java.

### Copying results

Every viewer — step and tool results, flow outputs, the Playground's answer, the file preview and Project files — has a copy icon. A click copies the content in its most useful form, and ▾ lists the others: HTML and Markdown as **formatted rich text** (pastes with its formatting into mail, documents and chat; plain text goes along for plain editors), or as source / text only; SVG as a **picture** (PNG) or its code; JSON rows and CSV as a **table** for spreadsheets, or as raw text; images as the image; anything else as text. Where the system clipboard refuses the modern API, text and rich HTML are copied the classic way.

### Finding and tagging tools

The Tools list has a search box (name, description or `#tag`), **Group by Source / Tag**, and tag chips that filter the list. Open a tool to add or remove its tags (built-in, managed, project, global and Copilot extension tools alike); tags are this user's, kept in the app's data folder, and do not change a tool or its approval.

### Archiving runs

The Playground and History lists have a search box, **Active / Archived**, groups (collapsible headings) and **Select** to archive, restore or group several runs at once; the open run has **Archive** / **Restore** and **Group…**. Archived runs are hidden, not deleted. **Appearance › Housekeeping** sets after how many days finished runs are archived automatically — separately for Playground prompts and for History (workflow steps and flow runs); 0 is never. It applies on save, at start and every 6 hours; running runs are never archived. Archived flow runs also leave the Run flows list.

### Built-in tools

16 agent tools compiled into the app (`internal/builtin`), so no one can modify them. Each is exposed as its own MCP tool by agentbridge and attached to every workflow step and playground prompt:
- **Read:** `read_file`, `list_directory`
- **Search:** `file_search`, `text_search`, `find_usages`, `workspace_changes`
- **Edit:** `create_file`, `create_directory`, `edit_file`, `move_path`, `delete_path`
- **Run:** `run_command`, `get_command_output`, `get_problems`
- **Web and plan:** `fetch_webpage`, `todo_list`

`fetch_webpage` returns a readable summary by default (`format: text`, for the AI: the URL and status, then the page's text, cut at `max_chars`, 20,000 by default). With `format: raw` it returns exactly the response body — an API's JSON as is, with nothing added before or after — for a later step to parse; it fails on an error status, binary content, or a body longer than `max_chars` (by default the whole response, up to 5 MB) instead of passing on cut data. A `fetch_webpage` step added in the Flow designer starts with `format: raw`, and arguments with fixed choices are dropdowns. With `format: json` (also the whole response by default) it returns the response wrapped in a JSON object, when the status and headers matter too: `url` (after redirects), `status`, `statusText`, `ok` (2xx), `contentType`, `title` (HTML pages), `headers` (lower-case names; cookies are never passed on), `json` (the body parsed, when it is JSON) or `body` (its text, HTML as readable text), `size`, `truncated` (the body was longer than `max_chars`) and `binary`. An error status is data in this mode, not a failure, so a Decision can check `ok` or `status`. The Flow designer knows this shape: a step after it sees the fields in its Data panel and path suggestions, e.g. a Loop with **List from** `json.items`.

Paths are confined to the workspace (symlinks included), deletes go to a trash folder, and output is redacted. IT can turn tools off per machine with `"disabledBuiltinTools"` in the policy file. Tested end to end with Claude Code 2.1.318 and GitHub Copilot CLI 1.0.107. After changing `internal/builtin/registry.go`, run `go run ./scripts/gen-builtins` to refresh the browser preview's copy.

### Credentials

The app never stores agent credentials. The CLIs use their own sign-in. A token pasted on the setup screen is held in memory for the session and passed to the child process as an environment variable. Secret values for tools work the same way. Token-shaped strings and known secret values are redacted from events and history.

### Copilot CLI extensions

Tools › **Copilot extensions** lists your own Copilot CLI extensions (`~/.copilot/extensions/<name>`, or `$COPILOT_HOME/extensions`) and the open project's (`.github/extensions/<name>`): what each says it does, the tools it adds (read from `extension.mjs`, nothing is run), its files and npm packages, and whether the project has the same copy. **Load into this project** copies one of yours to `.github/extensions/<name>` (without `node_modules`, `.git` or symlinks; at most 50 MB), and can install its npm packages there through the proxy and registries under Packages & proxy, adding `.github/extensions/*/node_modules/` to the project's `.gitignore`. When your copy changes, **Update the project copy** replaces it (the old one goes to SpecWright's trash); **Delete from project** archives the project copy (see below) and never touches yours. Commit the folder to share it with the team. SpecWright's Copilot runs load project extensions automatically (`--experimental` and `GITHUB_COPILOT_PROMPT_MODE_EXTENSIONS=true`, since `-p` mode skips them otherwise).

**Their tools become project tools.** Loading an extension approves it: SpecWright loads it once with the Copilot SDK stubbed (`internal/extension/copilotshim.mjs`), reads the tools it registers and saves each as a project tool of kind `copilot` in `.codegen/extensions.json`, with its parameters taken from the tool's JSON schema. From then on it works like any other tool: Claude and Copilot can call it through agentbridge, the flow designer lists it (badge **CP**), and Tools › Test with AI tests it. A call runs `node copilot-shim.mjs call <extension.mjs> <tool> '<arguments JSON>'` in the project folder, with no shell; the handler's return value (a string, `{ textResultForLlm, resultType }` or JSON) is the result, and the extension's own logging is shown only when a call fails. Approval covers every file of the extension, so a change, or an extension that came with a clone, shows **needs approval** until you approve it again. Its npm packages are installed in its folder on first use. Copilot hooks and session events only run inside Copilot.

### Deleting tools

**Delete tool** (on a project tool's page in Tools) archives it rather than erasing it: its files and its record from `.codegen/extensions.json` move to `.codegen/archive/<YYYYMMDD-HHMMSS>/` in the project, with an `ARCHIVED.md` saying what was moved from where and how to restore it (`tools/<name>/` holds the script or tool folder and `tool.json`). A Copilot extension tool takes its whole extension with it, since its tools share one folder: `.github/extensions/<name>` moves to `copilot-extensions/<name>` in the archive (without installed packages), next to `<name>.tools.json`; your own copy in `~/.copilot/extensions` is not touched. Agents and flows can no longer use a deleted tool. npm `ext:*` scripts are deleted in `package.json`, and global and managed tools are managed outside the project.

### Permission prompts

When Claude Code wants a tool it has no standing permission for (a write outside the project, a web fetch, a tool that is not pre-allowed), the CLI calls agentbridge's `permission_prompt` tool (`--permission-prompt-tool mcp__agentbridge__permission_prompt`), and the app asks you on top of whatever screen you are on: **Allow once**, **Allow for this run** (that tool, until the run ends) or **Deny**, optionally with a note telling the AI what to do instead. The run waits up to 10 minutes. Before this, `-p` mode denied such tools silently, so setups went wrong without anyone being asked. The headless runner asks on the terminal, or takes `-permissions allow|deny` for unattended runs. Copilot CLI has no permission callback; it runs with its own allow rules.

In the Playground, an answer that asks you something gets quick replies (*Yes, go ahead*, *No*, *Explain the options first*) and a reply box; every finished answer can be replied to, which continues the conversation.

### Choosing models

A model picker sits wherever AI runs: the Spec workflow (for its steps), the Playground, Files › Ask AI, Tools › Test with AI, Run flows (for AI steps) and each AI step in the flow designer, plus the app-wide model in Appearance › Account. Models are grouped as most capable, balanced, fast (and Auto for Copilot), with search and keyboard navigation; any other name the CLI understands can be typed in. *Default* means: the flow step's run, else the workflow, else the app-wide model, else the CLI's own default. Claude's list is its aliases (latest of each family) and full model names; Copilot's is read from `copilot help config`.

### Workspace files

- `.codegen/profile.json`: wizard profile (language, build tool, libraries, folders, rules, diagrams)
- `.codegen/workflows/speckit.json`: step inputs, instructions, options, status, budget
- `.codegen/extensions.json` and `.codegen/tools/{project,global}/*`: tools
- `package.json` scripts named `ext:*` appear as tools that need approval. Node.js is required to run them. Editing a script withdraws its approval.

Run `wails dev` for development. To use the UI in a browser with the mock backend, run `npm --prefix frontend run dev` and open http://localhost:5173.

### Signing the macOS app

`wails build` signs the app ad-hoc, so every build has a new code hash. macOS then treats each build as a new app and asks again for the Documents folder (and the keychain). `scripts/build-mac.sh` builds the app and signs it with a stable certificate, so macOS remembers what you allowed across rebuilds.

You need one certificate, created once. Either:

- **Apple Development (free):** in Xcode › Settings › Accounts, sign in with your Apple ID, then Manage Certificates › + › Apple Development.
- **Self-signed:** in Keychain Access › Certificate Assistant › Create a Certificate, set Name to `SpecWright Local`, Identity Type to Self Signed Root and Certificate Type to Code Signing.

Then build:

```bash
scripts/build-mac.sh
```

To sign an existing build without rebuilding, run `scripts/build-mac.sh --sign`. To pick a certificate yourself, set `SPECWRIGHT_SIGN_IDENTITY` to its name. After the first signed build, macOS asks one last time; old SpecWright entries under System Settings › Privacy & Security › Files and Folders can be removed.

### Building on Windows

Install [Go](https://go.dev/dl/), [Node.js](https://nodejs.org/) and the Wails CLI (`go install github.com/wailsapp/wails/v2/cmd/wails@v2.17.1`, the version in `go.mod`). Then, in PowerShell:

```powershell
scripts\build-windows.ps1
```

It checks the tools are installed, builds `build\bin\SpecWright.exe` and restores the `frontend\dist` placeholder. From cmd, or by double-clicking, run `scripts\build-windows.cmd` (same options). Options:

- `-Installer`: also build an installer with NSIS (`winget install NSIS.NSIS`). It installs the WebView2 runtime where it is missing (Windows 10 and 11 have it).
- `-Arch arm64`: for Windows on ARM.
- `-SignOnly`: sign the existing build without rebuilding.

Signing is optional. It stops SmartScreen warning about an unknown publisher once your certificate has a reputation. Secrets in Credential Manager work whether or not the app is signed. To sign, give a certificate from your store by thumbprint (`-CertThumbprint`, or `$env:SPECWRIGHT_SIGN_CERT`), or a `.pfx` file (`-PfxPath`, with its password in `$env:SPECWRIGHT_SIGN_PFX_PASSWORD`). Signing uses `signtool.exe` from the Windows SDK and timestamps the signature, by default with DigiCert's public server (`$env:SPECWRIGHT_TIMESTAMP_URL` to change it).

Headless example (the mock agent needs no CLI):

```bash
go run ./cmd/headless -workspace ~/src/orders -agent mock -init claude -approve auto -input constitution="Tests for every service" -input specify="An order service"
```

Run one free-form prompt (the Playground without a window):

```bash
go run ./cmd/headless -workspace ~/src/orders -agent copilot -prompt "Find the TODOs and fix the first one"
```

Other flags: `-model sonnet`, `-permissions ask|allow|deny`, `-workflow file.json`, `-steps plan,tasks`, `-json` (JSONL events), `-runs`, `-replay <run-id> -speed 4`, `-reset`.

Tests: `go test -race ./...`

## Development wizard libraries

- **Corporate libraries (global):** skills an admin publishes for the whole app, like managed tools. They live in a signed catalog (`<store>/managed-libraries.json`, plus an optional IT-deployed `managed-libraries.json` next to the machine policy). They can be created, edited, published (a local copy can be signed into the catalog) and retired only in admin mode. Verified entries are copied into each project's `.codegen/skills/global/<name>/SKILL.md` when a project opens, before each run and after every change; edits to the copy are overwritten, tampered or untrusted entries are removed, and the copies are git-ignored. Local, unmanaged skills in that folder stay and show as "local copy".
  - **Corporate skills can have files too:** in admin mode a published corporate skill shows **+ Script** and **+ File or doc**. Its files (docs in sub-folders, `scripts/`) are stored in the catalog entry and signed with it, so changing one publishes a new version, and they are copied into every project's `.codegen/skills/global/<name>/` (scripts executable). A changed or extra file in a project's copy is put back on the next sync, and an edited file in the catalog fails the signature check. Publishing a local copy brings the files in its folder along. Skills without files keep their old signature format, so earlier signatures still verify.
- **Project skills and scripts:** plain files any user can create, edit, rename and delete in the wizard: skills in `.codegen/skills/project/<name>/SKILL.md` (or `<name>.md`). Deleting moves them to SpecWright's trash; renaming keeps the selection.
  - **A skill is a folder:** besides `SKILL.md` it can hold sub-folders of docs, references and other files (e.g. `docs/api.md`) that `SKILL.md` links to with relative paths, and its scripts in `scripts/` (saved executable), e.g. `.codegen/skills/project/orders/scripts/gen-dto.sh`. The wizard lists each skill's files with **+ Script** and **+ File or doc**; a single-file skill becomes a folder when you add one. When the skill is selected, the agent is told every file in its folder.
  - **New script** puts the script in a skill's `scripts/` folder (the AI can write it from a description). Scripts in the older shared `.codegen/scripts/` still work and can still be made there.

## Flow designer

Tools › Flow designer strings tools together into flows, stored as `.codegen/flows/<id>.json` (`internal/flow`).

- **Canvas:** drag tools and steps from the palette, drag a step's ● port to another step to connect, Delete removes, ⌘/Ctrl + scroll zooms. Edges set the order; a step can use the outputs of the steps before it.
- **Steps:** an Inputs step, tools (arguments are templates, or *describe it*: a free-form request from which the agent, after investigating the project's schema files, migrations, models and docs — and, if needed, calling the tool read-only to explore — builds the arguments; values you fill in stay fixed, and the run shows the chosen arguments and why), AI prompts, merges (join as text, JSON object, JSON array, template) and transforms (template, trim, case, truncate, keep matching lines, regex extract/replace, lines → JSON, JSON path/pick/format/minify, JSON → string (stringify) and string → JSON (destringify), CSV ⇄ JSON, Markdown → HTML, HTML → text, AI). **Stringify** turns JSON into a JSON string (`{"a":1}` → `"{\"a\":1}"`), for a tool or API that wants JSON inside a string field; **destringify** turns such a string back into JSON (strings encoded twice too). Both take an optional field path to change only that field and leave the rest — `body`, or `items[*].payload` for every element. **JSON → JSON (template)** reshapes JSON: write the JSON to produce with `{{this.<path>}}` placeholders (a placeholder that is a whole string value, `"{{this.total}}"`, keeps its type: number, list or object; inside a longer string it is text), and optionally a list path such as `items` (or `orders[*].lines[*]` to flatten nested lists) to apply the template to each element and get an array. Nested lists are reshaped with each blocks: an object whose only key is `"{{#each this.lines}}"` becomes a list, its value being the template for each element (inside a list, the elements are spread in). Inside a block `{{this}}` is the element, `{{parent.<path>}}` the level above (`parent.parent.…` further up), `{{root.<path>}}` the whole input and `{{this_index}}` the position; object keys can use placeholders too. Keys keep their order, both the template's and the input's for copied objects.
- **Several steps at once:** ⇧-click or ⌘-click adds or removes a step from the selection, drawing a box on the empty canvas selects the steps it touches (with ⇧ held, adds them), ⌘A selects all and Esc clears. Dragging one selected step moves them all and Delete removes them all. **⌘C** (or **Copy** in the inspector) copies the selected steps with the connections between them and the inputs they use, to the system clipboard as JSON; **⌘V** pastes them into the open flow (or another flow, or another SpecWright window): they get fresh step ids, their references to each other follow, the inputs they need are added, they are placed beside the existing steps and stay selected. **Paste … as a new flow** in the Flows list (or **Copy to a new flow** in the inspector) starts a new flow with them, and **Duplicate** copies them in place.
- **Connections carry data:** a step always gets the output of the steps connected into it. Tools receive it on standard input and in a file named by `$SPECWRIGHT_INPUT_FILE` (plus `SPECWRIGHT_STEP` and `SPECWRIGHT_RUN`), whether or not an argument uses it; a field that wants a file can be set to `{{input_file}}` (the path of that file; a literal `$SPECWRIGHT_INPUT_FILE` typed into a field is replaced the same way, since tools run without a shell); AI prompts get it appended when they do not mention it; merges, transforms and outputs use it by default. Connecting a step into a tool fills its best-matching empty argument with `{{steps.<id>}}` (from Inputs: arguments named like an input), the connection is labelled with the argument it feeds (or "stdin" / "AI"), the inspector has "← step" buttons to use an output as an argument, and a warning flags a tool whose arguments ignore its input.
- **Any earlier step's output:** `{{<step>.output_file}}` is the path of the file a step's result was saved in (`steps/<step>/output.<ext>` in the run's results folder, written for every step, even one that printed nothing), and `{{<step>.buffer_output}}` is the result text (`{{<step>.buffer_output.json.<path>}}` reads into JSON). `<step>` is the step's id (shown and editable as **Step id** in the inspector, e.g. `{{todos.buffer_output}}`), so a tool can read any step that ran before it, not only the one connected into it. Titles are only labels; flows saved earlier that referred to a step by its tool name or title are moved over to ids when they are opened. `{{steps.<id>.output_file}}` and `{{steps.<id>.buffer_output}}` work too. The "← step" buttons and auto-wiring use these (`output_file` for fields with "file" in their name), the Insert chips list them per earlier step, the validator flags unknown or not-yet-run step ids (and says which id a title or tool name means), and changing a step id updates them. `{{input_file}}` still means "the results of every step connected into this one, as a file", and is now written even when those steps printed nothing.
- **Variables:** `{{inputs.name}}`, `{{steps.<id>}}`, `{{steps.<id>.json.items[0].name}}`, `{{context}}`, `{{skills}}`, `{{input}}` (transforms), `{{output}}` (output actions); renaming a step updates every reference.
- **Loops:** a **Loop (for each)** step splits a list into items: a step's output, or a template. It can split one per line, a JSON array, CSV rows or the matches of a pattern, with a filter, a maximum, and an option to skip repeats. When the list arrives inside a JSON object (a Loop connected to the Inputs step gets `{"stocks": "AMZN\nMSFT"}`), **List from** names the field that holds it (`stocks`, or a path like `data.items`; the field box suggests them); left empty, the object's only field or its only list is used, and a Loop connected to Inputs picks the input itself. A field holding text is split as chosen (one item per line by default); one holding a JSON array gives its elements. Every step after it runs once per item, tools and AI prompts included, until a **Gather** step collects the results: joined text, `## item` sections, a JSON array, a JSON object keyed by item, or a template per item. Inside the loop, `{{item}}`, `{{item.json.<path>}}`, `{{item_index}}` and `{{item_count}}` are set (for the innermost loop). Loops can be nested: use the loop's step id to read its item, e.g. `{{files.item}}`, `{{symbols.item.json.name}}`, `{{files.item_index}}`. An item's failure stops the loop, unless *keep going* is on (then its error is gathered). Each item's result is saved under `steps/<step>/items/`. AI steps inside a loop are reviewed only when marked.
- **AI designer:** **✦ New flow with AI** (in the Flows list, and on the empty Flows screen), with its own **Model** picker, takes a description in plain words — no need to know the tools — and proposes 2–3 complete flows; each option card shows its steps as a path, the tools it uses, whether it needs AI ("No AI" or "AI in N steps") and why, and **Use this flow** creates it and opens it on the canvas. The agent is given the step types and the project's runnable tools with their contracts (parameters and output shapes, compactly) and must prefer existing tools, then deterministic steps wired by those shapes, and AI steps only where nothing else fits. Every option is checked in the app before it is shown: step ids and tool names are corrected, it is validated against the real tools, and it is **tried**: the agent supplies realistic sample inputs, a mock output for every tool and AI step (else one is made from the tool's output shape or the step's expected reply) and what each output should contain; the app then runs the flow end to end with those mocks — every other step really runs, nothing is saved and no tool is called — and checks that every step on the path runs, required tool arguments get a value, an output is reached and has content, and the expectations hold. Options that fail validation or their trial get one automatic repair round with the failures (the card shows **✓ Tried** or **✗ Trial failed** and the trial: each step's status and sample output, the path taken, the checks), and options are ranked: ones that check out first, then fewer AI steps, then more of your tools. Token use is shown on the panel and counted in Metrics.
- **Fixing a step (Run flows):** after a run, each failed step has **✦ Fix with AI** and each finished step **✦ Improve** (with a Model picker and an optional note on what is wrong or should be better). The agent sees the step, what reached it in that run, its error or result, and how the steps after it use it, and may change only that step's definition (its settings, or its type or tool) — same id, same connections. The suggestion shows what changes (before / after) and whether it checks out. **Try it** runs a trial: an unsaved copy of the flow where the steps before the changed one reuse the run's results (they are not run again — no tools called, no AI used) and the changed step and the steps after it run for real; the trial run is marked **trial** in the run list. On the trial, **Apply to the flow** writes just the changed step into the saved flow, **Discard** goes back to the earlier run, and a trial's steps can be fixed or improved again before applying.
- **Data shapes:** the designer knows what data every step gets and gives — nested objects and lists, with types and descriptions — and shows it in the inspector's **Data** panel: the fields as a tree (click one to put its path or `{{…}}` variable where you are typing), the shape in one line, and where it comes from: *declared* (a tool's output shape, an AI step's **Expected reply**, the flow's inputs), *worked out* from the steps before (Filter, Aggregate, Decision, Loop, Gather, Merge and Transform's JSON operations derive their result from their input), or *learned* from sample data or the flow's last run. Path boxes (conditions, group by, sort, JSON paths) suggest the fields, and the validator warns about a field or `{{<step>.buffer_output.json.<path>}}` the shapes say is not there. **Flow settings › Interface** shows the flow's inputs and output shapes and copies them as JSON Schema. Shapes are designer metadata and cost no tokens: the AI is given a compact shape only for an AI step's expected reply (it is asked to reply with only JSON in that shape, and code fences are stripped) and for a JSON parameter it fills in; tools' output shapes are never sent.
- **Flow step guide:** “How to use them ↗” above the designer's step list, and “How to use ↗” in the inspector of a selected step, open a guide to every step type — AI prompt, Merge, Transform, Loop, Gather, Decision, Filter, Aggregate and Output — with when to use it, how to use it, its settings and three or four examples each. Each example shows its sample input, the step's settings and the result, previewed live by the app (AI results are typical answers); **Try it in the designer** saves the example as a flow (“Example: …”) and opens it with the step selected.
- **Decisions:** a **Decision** step checks the data from the step before and sends the flow down a path. Each path has a condition, and the connections out of the decision are each put on a path (click a connection to choose it), or on **Otherwise**, which is taken when no path matches. The steps on the paths not taken are skipped ("not on the path the flow took"), and steps where the paths meet again (a merge, an output) run with what the taken path produced. Paths are checked in order; the decision takes the first that matches, or every one that matches. The data passes on unchanged, and the run shows the path taken. Decisions work inside loops too, per item.
- **Conditions** (decisions and filters) are groups of rules joined by *all of*, *any of* or *none of*, and a rule can be a group itself, so conditions nest to any depth. A rule compares a field — a path into the data: `status`, `customer.address.city`, `items[0].sku`, `items[*].qty` — with =, ≠, >, ≥, <, ≤, contains, starts / ends with, matches a pattern, is one of, is between, is empty, exists, is true, or a count / length. Numbers compare as numbers and everything else as text (so ISO dates compare correctly); a list matches when any element does, or every element when ticked; text comparisons can ignore case. Values can use variables, and `{{this.<field>}}` compares two fields of the same data.
- **Filter** keeps (or drops) the rows that match a condition, optionally dropping repeated rows, sorting (`-total` for high to low) and keeping at most N. **Aggregate** groups rows (*Group by* `region, customer.tier`) and calculates values: count, distinct count, sum, average, min, max, median, first, last, list, distinct values, join as text. In window mode every row is kept with values over its group added — row number, rank, dense rank, running sum / count / average, the previous or next row's value (lag / lead), % of total, bucket (ntile), and any of the group values — like SQL's `OVER (PARTITION BY … ORDER BY …)`. Both read a JSON array (or an object holding one), CSV with a header line, or one row per line, and write a JSON array; a list path like `items[*].qty` sums or counts nested values.
- **Inputs:** text, long text, number, yes/no, choice, multiple choice (checkboxes; the ticked options reach the flow one per line, ready for a Loop), file, files and clipboard, with defaults (including pasted, dropped or picked files). A **secret** (password, API key, token) is masked as it is typed and never saved: it has no default, and the run state, run history, step outputs and saved results show `••••••••` or `[REDACTED]`. Steps get the value only through `{{inputs.name}}` (for example in a tool's arguments); the Inputs step's own output masks it, so it does not reach an AI step by accident. It lives in memory for the run only, so trying a step fix after restarting the app asks you to run the flow again.

  Where a secret comes from is set on the input (the flow file keeps only where to look, never the value):

  - **Ask in the run form** (default): typed when the flow runs, masked, with Show/Hide.
  - **System Keychain:** read when the run starts, nothing to type. By default SpecWright's own entry (service `SpecWright`, account = the input's name); any other entry works too: a password saved under another service and account, or an internet password saved for a server (e.g. by Safari). macOS asks once before reading an entry another app saved; the prompt names `security` (the command SpecWright reads the Keychain with). Choose **Always Allow** so later runs don't ask, even after SpecWright is rebuilt. The designer can check the entry and save a value into it. When nothing is found, the run form asks, with **Save to Keychain** for later runs.
  - **On Windows** the same source reads and writes **Windows Credential Manager** (Control Panel › Credential Manager › Windows Credentials). SpecWright's entries are generic credentials named `service/account`, e.g. `SpecWright/github-token`; to read one another program saved (git, cmdkey), give its *Internet or network address* as the service. Windows has no internet passwords, so that option is macOS only. On Linux it is the Secret Service (`secret-tool`).
  - **Environment variable:** for headless and CI runs.
  - **Keychain, then environment, else ask.**
  - **Ask in a dialog during the run:** asked once the run has started (scheduled runs ask when they start; headless runs ask on the terminal). "Remember for this session" keeps it until the app quits.

  To use a secret in a tool step, pick **🔒 Secret…** next to the argument (shown for arguments that look like passwords, and for text arguments once the flow has a secret), or choose **+ New secret input**. The designer warns when a secret is sent to an AI step, and when something that looks like a password is typed into a tool's arguments. When the AI fills in a tool's arguments, it sees secrets masked; the real values go back in before the tool runs. Saving to the Keychain never puts the value on a command line, where other programs could see it.
- **Context and skills:** free text plus files, and skill files from the project's libraries or attached.
- **Outputs:** md, txt, html, csv or json (content is converted: JSON → CSV/Markdown table, Markdown → HTML, …), with actions: save to a project file, call a tool, copy, show. Several outputs per flow.
- **Checks and previews:** the flow is validated as you edit (missing tools or arguments, unknown variables, steps used before they run, loops, unsafe save paths); merges, transforms and outputs can be previewed with sample data.
- **Import/export:** one portable `.flow.json` with its skill, context and default input files embedded; importing puts those under `.codegen/flows/assets/<id>/` and gives the flow a free id.

### Running flows

Tools › Run flows executes a flow (`internal/core/flowrun.go`):

- **Setup:** fill the inputs (text, files, clipboard…), check the credentials the flow's tools need, and set options: when to pause for review (after AI steps and marked steps, every step, only marked steps, never), repeat N times, run once per item of an input (lines, a JSON array or CSV rows) keeping only items that match a pattern, a start time, run and step timeouts, steps to skip and a step to stop after, the model.
- **Credentials:** secrets come from the session, the environment variable or the system keychain (macOS Keychain via `security`, Linux Secret Service via `secret-tool`, service "SpecWright"); a missing one pauses the run and asks, with the option to save the answer in the keychain. Secret values are redacted from every step's output before it travels on.
- **Review:** a paused step can be accepted, accepted without further reviews, or stopped; or improved first — refine with an AI prompt, run a shell command on the result (stdin → stdout), edit it, or change the step's settings and run it again. Each improvement can be used once or saved into the flow (added to the AI prompt, inserted as an AI or command step, or as the new settings).
- **Progress:** a sidebar shows progress, the steps, elapsed time, tokens, cost or premium requests, AI calls, tool runs and outputs; outputs are rendered by format with their saved files. Runs are recorded like other runs (History, Playground) and in the usage ledger: Metrics shows flows executed, completed/failed/stopped, tool executions, AI calls, hours saved (the flow's "minutes saved per run", or an estimate) and cost per flow.
- **Playground:** flow runs appear in its list; selecting one shows the steps and the live Activity and Debug log, which now use icons per event kind.

## Run results and continuing conversations

Every run (Spec workflow steps, Playground prompts, Files › Ask AI, flow runs) gets an id of its start date and time plus a random UUID, e.g. `20261110-142233-3f2a8c1e-7b3d-4a60-9c1e-0b9d2f5e8a71`. When it ends, its results are written to `.codegen/runs/<YYYY-MM-DD>/<run id>/` in the project (git-ignored):

- `summary.md` (what ran, when, how it went, usage, the answer), `run.json` (the record), `prompt.md` (the prompt as sent), `answer.md`, `tools.md` (tool calls and results), `files.md` (files changed), `events.jsonl` (the redacted event log)
- `tools/<n>-<tool>/input.json` and `output.<ext>`: each tool call the agent made (the extension follows the content: html, json, csv, md or txt)
- flow runs also `state.json`, `steps/<step>/input.txt`, `args.json` and `output.<ext>` (tool steps save these as they run; `{{input_file}}` points at the saved input) and `outputs/<n>-<title>.<format>`

Tool output is shown the same way everywhere (Playground tool calls, Run flows steps, outputs and reviews, Tools › Test with AI, built-in tools): a **Preview / Raw data** toggle (HTML rendered, Markdown formatted, JSON and CSV as tables), links to the saved input and output files (they open in the quick preview, which has the same toggle), **Open in preview** and **Copy**.

Every run screen (Spec workflow, Playground, Run flows, History) links the folder and its files (they open in the quick preview), copies the run id and, in the desktop app, shows the folder in Finder.

**Continuing:** in the Playground, *Continue this conversation* (or *Refer to earlier runs…* to pick any prompts, workflow steps or flow runs; Run flows and History have *Continue in the playground*) makes the next prompt carry the earlier runs: their questions, answers (shortened) and results folders, oldest first, so the agent can read more. Follow-ups chain into threads shown above the new question. Headless: `headless -prompt "…" -continue <run-id>[,<run-id>…]`.
